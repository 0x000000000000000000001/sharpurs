**H04 is validated: 70/100 points, 4 of 7 milestones in maintenance cycle 2.**
The next milestone is H05, the Sharpurs-specific CLI contract.

## Changes and intentional behavior corrections

- `Project.writeModule` returns `ModuleFiles`, containing the emitted F# filename
  and optional C# filename. Unchanged sources still enter this invocation's
  inventory. `Main` collects successful emissions and supplies them to finalization
  in the sequential builder's dependency order.
- F# compile items use that order, surrounded by the fixed prelude and entrypoint.
  C# compile items are the sorted current C# filenames. Finalization no longer
  discovers sources by reading the output directory.
- An old `.cs` left in `output/Main/` no longer silently enters the C# project.
  Removed module/native sources may remain on disk but are excluded. When the last
  C# FFI disappears, the generator removes its obsolete `FFI.CSharp.csproj` and
  omits the project reference.
- `Project.FileSystem` owns directory creation, optional reads, write-if-changed
  and removal of the fixed obsolete project. Only `ENOENT` means an absent file;
  `EEXIST` is accepted for directory creation only after confirming a directory.
  All other failures propagate with the path, Node error code/syscall and original
  cause. Failed reads never authorize a write.
- An unreadable `sharp.packages.props` now fails generation instead of silently
  dropping application dependencies. It remains an optional, verbatim F# project
  `ItemGroup` fragment. Application-owned code can use an explicit
  `ProjectReference`; paths are relative to the generated project directory.
- Generated files retain their timestamps when their text is unchanged.
  `output/Main/corefn.json` and application-owned files remain inputs, outside the
  generated-source inventory.

### Project lifecycle and failure coverage

The dependency-free PureScript fixtures compile to real TAST. Their F# dependency
order differs from alphabetical order; the C# sources require stable alphabetical
order. A separate application project is explicitly referenced and its value is
checked by the executable. Invalid stale F# and C# files are present throughout.

The seven phases are mixed generation, mixed incremental replay, removal of an
unreferenced module plus replacement of one C# FFI by F#, its incremental replay,
replacement of the last C# FFI, F#-only incremental replay and clean regeneration.
The tests check exact compile-item inventories, preserved stale-source bytes,
removal of the obsolete C# project, complete current-output equality after clean
generation and unchanged nanosecond mtimes on incremental replays. Every phase
also checks `Main/corefn.json`, an application-owned file and the invalid leftover
sources for content and timestamp preservation.

Production project operations are exercised against actual filesystem failures:
missing/non-directory output parents, a file occupying the output-directory path,
directories where readable text is expected, an unremovable obsolete project,
an unreadable reference fragment, a writeable-but-unreadable output, a changed
read-only output, and directory permissions preventing new file/directory creation.
Each assertion checks the diagnostic path, code and original cause. Absent optional
references and unchanged read-only outputs also succeed. Permission bits are
restored in `finally`; temporary workspaces are isolated from application inputs.

The immutable H03 bundle was replayed with the same project test. It exits 1 at
the first compile-item assertion because `Leftover.cs` appears in its C# project.
That expected historical failure and the passing H04 replay are both retained.
